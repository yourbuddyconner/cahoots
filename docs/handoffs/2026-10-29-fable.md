# Fable handoff: website, docs, and the circle experience

Date: October 29, 2026. This handoff accompanies the website/docs changes committed to `main`. It distinguishes implemented work from proposed product direction.

## Where the user wants to go

The initial request was to replace the landing page’s unreadable copy and character illustration. The user liked the replacement layout, then asked for a more deliberate brand, matching docs/journal, the current PCB badge model, and a substantial docs readability pass.

The discussion then moved to the product: **what people do after creating a circle**. The user wants the app ecosystem to be prominent. They expect badges relatively soon, likely connected to desktop applications over USB. Phones and browsers should primarily support chat. A Cahoots-hosted default relay would remove server setup from circle bootstrapping.

Latest clarification: **do not make a concrete phone-to-badge connection a prerequisite**. The user suggested widening a circle with a badge and is open to optical exchange between a phone and laptop, including randomness. The exact enrollment/membership design is not decided. The user authorized recommendations on phone/browser roles, not implementation of an arbitrary new membership protocol.

The source CAD lacks local models for SW1/SW4 and U2. SW2/SW3 have alternate models that export. These omissions are documented in `site/README.md`; the viewer does not invent substitute geometry. The board remains a design/prototype, not proof of completed hardware validation.

## Recommended product model

These are recommendations discussed with the user, not all finalized requirements:

1. **Phone web app and browser:** useful independent chat clients. A software circle can be useful beyond a disposable demo. Native phone implementation can follow a coherent web experience.
2. **Badge over USB:** hold secrets and authorize sensitive desktop operations. Enrollment approval is a future capability, subject to the circle’s rules.
3. **Default hosted relay:** make the first chat work immediately, while retaining a custom-relay option. The relay delivers ciphertext; it is not the source of keys or membership authority.
4. **Circle home:** show useful tools, setup state, and activity after creation. Avoid a screen that merely lists cryptographic primitives or promises unavailable integrations.

### Distinguish the three enrollment questions

- **Another device for an existing member:** aim for application-scoped authorization and keys. Do not copy the entire live pad/send ledger to a second independent spender.
- **Another person:** requires membership rules and fresh keying for future messages. One badge may authorize this only if the group explicitly delegates that authority.
- **Adding a badge later:** cannot revoke secret copies already present on phones. Moving to badge-held custody needs a fresh cryptographic generation and an explicit transition. Conversation continuity can be a product feature without pretending the old secrets moved exclusively into hardware.

Old members cannot be made to forget plaintext or keys they already received. A membership change must define history access and future access separately.

### Optical exchange

The browser already implements animated QR/fountain transport and accepts extra randomness from a camera. The proposed reverse direction, phone to laptop, can reuse those building blocks; it is not implemented as a complete provisioning workflow.

For enrollment, use a recipient public-key request and an approved encrypted response bound to that recipient. Define verification, consent, replay prevention, and expiry. QR is the transport, not authentication by itself.

Phone-generated bytes remain software randomness. Extra entropy should supplement the receiving application’s own source. It does not confer membership, transfer authorization, or automatically qualify the circle for a hardware-randomness label. The existing UI accepts a file/camera source as “hardware randomness” without independently proving its origin; review that labeling before expanding this flow.

### Key delivery is real implementation work

Current chat sessions consume pad ranges (`crates/chat/src/session.rs`). The proposed phone design instead derives per-epoch chat keys from a circle root. Root derivation helpers exist in `crates/core/src/root.rs`, but that does not make the proposed session path complete.

The chip wire API has a generic `SealKey { label }`, not a complete paired-client, epoch-scoped chat enrollment API. Do not expose a reusable root/seal key and describe it as access to only one epoch. Define a narrow key-release operation and adapt the chat session API deliberately.

## Recommended next milestones

### 1. Hosted delivery and first chat

Acceptance: two clients complete a ceremony and exchange chat messages through the default relay without entering an address. Preserve a custom-relay override.

Before deployment: choose host and domain, configure HTTPS, persistent log storage, health checks, request limits, and an explicit retention policy. The current station has no built-in rate limiting. Its Dockerfile uses Rust 1.88 while the repository pins 1.94; align and build it. Relay hosting was not deployed or selected here.

### 2. One USB badge workflow

Choose one useful desktop operation and make it work end to end, first against the simulator, then hardware. Include consent, unplug/reconnect behavior, and a clearly defined custody boundary. Verify browser/native platform access rather than assuming every mobile browser can use USB.

### 3. Scoped enrollment and membership changes

Specify and test authorization policy, identity of the new client/member, key generations, history access, replay protection, revocation, and safe persistence. Keep routine messaging usable without a live badge connection.

### 4. One shared app, then a runtime

Start with a narrow shared-board experiment. A trustworthy member-counted vote needs individually authenticated events: the current chat sender field is a claim, and any group member can derive another sender’s chain. The relay’s ordering is also not verified consensus.

The runtime needs app IDs/versions, explicit enablement, scoped encrypted events, deterministic replay, data permissions, resource limits, upgrades, and removal. Keeping pad bytes private does not stop an app leaking plaintext it can read.
