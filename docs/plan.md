# Roadmap

Status reflects the `main` branch as of 2026-10-29.

![Roadmap by track](diagrams/roadmap.svg)

## How to read this page

The work runs on five tracks. Each milestone has a short code, such as `M2`, that commit messages and issues refer to.

| Track | What it is about |
|---|---|
| Hardware | The badge, from a software-only simulator to the device we manufacture |
| Toolkit | Libraries that plug the shared secret into tools people already run |
| Networks | Using a group's secret to set up VPNs and mesh networks |
| Chat | Encrypted group chat and the public feed it runs over |
| Apps | Small programs that run on top of a group's message stream |

Status words mean this:

- **done**: the code is merged and its tests pass in CI.
- **partly done**: some of the scope is merged. The row says what is missing.
- **up next**: the next thing to start on that track.
- **later**: waits on another milestone, named in the row.

A few terms repeat below. The [glossary](glossary.md) defines all of them. The ones you need most: a **circle** is a group that shares one secret, and a **cahoot** is the face a badge draws for itself. The **pad** is that secret, a file of random bytes. The **feed** is the public bulletin board that carries encrypted messages. A **hosted seat** is a group member that is a program running in a secure cloud enclave instead of a person with a device.

## The first product: what ships first

*Added 2026-10-29. This section orders the work on this page toward one product experience. It merges the [handoff of 2026-10-29](handoffs/2026-10-29-fable.md) with the chip, SSH and git work (M4f) and the phone-app design. The milestone codes below are the ones in the track tables.*

The experience: two or more people meet, make a circle with the phones and laptops they have, and are chatting before they part, with no server to set up and no account to make. A member with a badge plugs it into a laptop and logs into servers and signs commits with a key that never leaves the chip. Everything else on this page comes after that works for real people.

## Toolkit

Goal: a developer who already runs WireGuard, encrypts files, or signs approvals can use a group's secret without learning the protocol.

| S1 File and tunnel keys | A library that hands out keys from the pad and records what was used, plus adapters for HPKE, `age` file encryption, and WireGuard | Two laptops encrypt a 1 GB file to a group. A reused key is refused. The key-derivation test vectors are published | **done** (the end-to-end run with the real `age` command is still pending) |
| S4 More tunnels | Adapters for TLS 1.3, MLS group messaging, and a finished WireGuard helper | Each adapter has a test against the real implementation | partly done: the WireGuard helper and its test against the real `wg` tool are done (see N1); TLS 1.3 and MLS remain |
| S2 Approvals | A verifier that a policy engine can require: "a member of this group approved this action, at this assurance level". The approval object and its check against the manifest are in `cahoots-objects`; what remains is the adapter a policy engine calls, which also checks that the seat is still a member and that the approval's log position is inside the window the policy allows | A forged, replayed, expired or revoked-seat approval is refused, with a test for each | partly done: the object, the verifier and the vectors shipped at M1c (2026-10-26); the adapter waits on C6 for revocation |
| S6 Grants as web tokens | A program on a laptop or a server that presents a badge-born grant to the web world without re-signing it: the grant's JSON projection as an OAuth 2.1 access token with structured authorization details (RFC 9396), bound to the holder's key by DPoP (RFC 9449), and an approval as evidence a decision service that speaks AuthZEN can ask for by assurance level. | S7 Sealed objects | Receipts and private facts sealed to the circle under a key the pad derives for a period, the way tunnel keys are, with the pad spent once per key and not per object. A store that holds them learns that something was posted and nothing more; any member can open them later. This is also the pad budget that lets a node post a reading a minute | A receipt sealed on one device opens on every member's device, a reading sealed for a period and lifted into a later period is refused, and a day of readings at one a minute spends one key's worth of pad | after M1c; needed by M4g. The chat crate's key schedule is the starting point |
| S3 Recovery | A recovery secret split among the group at the ceremony, so that any 3 of 5 members can restore it | Three shares recover the secret. Two shares reveal nothing | after M5 |
| S5 Hosted keys | A copy of the pad held in a cloud enclave, so a server can take part under a pinned policy | The server gets a key only when the policy allows it, and every use is logged | after M3 |

## Networks

Goal: a group that met once can set up a VPN or a mesh network with no coordination server and no certificate authority. The current tools are summarized in [Apps for your circle](apps.md); the milestones below track the remaining network work.

| Milestone | What it delivers | Done when | Status |
|---|---|---|---|
| N1 WireGuard | A command that sets up and rotates WireGuard tunnels between group members from the pad alone, with the handles and announcements carried by the feed or pasted | Two Linux hosts bring up a tunnel whose keys came only from the group. Rotation works. A replayed key is refused on both ends | **done** (2026-10-21): `scripts/wg-demo.sh` runs in CI between two network namespaces |
| N2 Control messages | Standard message types for "here is my public key", "here is a key for our tunnel", and "rotate now" | Test vectors are published and the app shows peer announcements | **done** for the format and the vectors (2026-10-21); the app does not show announcements yet |
| N3 Headless nodes | A way to hand a node with no screen, such as a router on a roof, its share of the pad from a badge, with the badge wiping its copy | A simulated node receives its share from a simulated badge, and the badge's copy reads back empty | after M4a, then M4b |
| N5 Federation | Pairwise secrets between each two members, so a member cannot forge another member's messages | Three devices complete the group and pairwise ceremonies. A member cannot post as another | after M4b |

N1 and N2 shipped first, because they needed no hardware. A Tailscale-like mesh still needs two more things: a `mesh` command that loops the pair steps over every announced peer, and a relay for hosts behind NAT, which WireGuard cannot do on its own.

## Chat

Goal: a group chat where the keys come from the circle root and the messages travel over a public feed. Chat is as secret as the root. The design is in [Chat](chat.md).

| Milestone | What it delivers | Done when | Status |
|---|---|---|---|
| C1 Chat crate | The chat encryption: keys derived from the circle root in numbered epochs, a chain per sender that deletes each step once used, standard authenticated encryption. | C2 The feed | The public relay (the Numbers Station): an append-only log where each entry is chained to the last, and which refuses any pure-pad message that reuses pad bytes | Posting and reading work over HTTP. A tampered log refuses to start | **done** |

| C4 Chat in the app | A chat screen in the browser app, with a relay address setting | Two browser tabs chat through the relay | **done** |
| C7 Default relay | The app ships with a default relay so a new circle chats without entering an address, and keeps the override for a relay a member runs. The station gets what a public relay needs before it is exposed: a per-client rate limit, a cap on the log file, a container that builds with the pinned toolchain, and a deploy recipe in `deploy/relay`. The relay stays what it was: ciphertext by circle, no keys, no membership | Two browser contexts complete a ceremony and chat through a station without either entering an address (`web/e2e.mjs`); a client past the rate limit gets `429`; a full log answers `507`; the station at `relay.cahoots.network` answers `/healthz` | **done** (2026-10-29): `relay.cahoots.network` answers `/healthz` over HTTPS from Fly (one machine in sjc, a 1 GB volume); the browser check chats through a local station |

| C5 Hosted feed | The relay running inside a [Turnkey Verifiable Cloud](https://docs.turnkey.com/features/verifiable-cloud/overview) enclave, with the head of its log anchored so it cannot be rewritten | The deployment pins the exact image, and the log head is anchored | after C2, needs [TVC](https://docs.turnkey.com/features/verifiable-cloud/overview) access |

14. Device tiers below T3 are declared, not proven. Since M1c a seat's tier is bound into its commitment and signed into the manifest, so it cannot change after the fact, but nothing checks it until the chip's attestation at M4f. 15. **New, 2026-10-21.** Hardware. Decided: three boards. The DIY build on an Arduino Nano ESP32 (`crates/esp32s3`), V1 (a Pico 2 soldered onto our own board, M4b) and V2 (the Baochip Dabao, RISC-V, T3, M5). All three get the 1.54" e-paper and two buttons, and no joystick. More boards can join through the HAL. Open: whether a badge's PIN is entered on the badge or on the phone.
16. **New, 2026-10-26.** The key store chip (M4f) raises three questions that are not settled. What a phone tapping the badge over NFC should be able to do: the interface is kept, off by default and switched on from the menu, and the keys the consent screen guards are reachable only from the Pico, so the question is which objects a hacker may expose over it and whether the firmware should be told about every tap. Whether Cahoots ever signs a chip's factory key to say "this is a Cahoots badge": that is a certificate authority with our name on it, and the plan is to keep it optional and away from anything the pads depend on. And which signature the badge uses for its identity, Ed25519 from the chip or a hybrid with ML-DSA in software, which decides the request size cap.
17. **New, 2026-10-26.** Time. Every signed object carries a log position and no wall-clock time, because a badge has no clock it can trust. A grant that becomes a web token (S6) needs an expiry in seconds. The plan is that the laptop program supplies the clock and the verifier treats it as an outer bound, with the log position as the binding one. Open: whether a badge ever gets a real-time clock, and what it is allowed to say with it.
18. **New, 2026-10-26.** A duress PIN. Nothing in the design helps a person pressing both buttons under threat. Hardware wallets answer with a second PIN that opens a decoy. Whether a badge should, and what a decoy circle would look like, is open, and it interacts with where the PIN is entered (decision 15).
19. **New, 2026-10-26.** Whose floor wins. The manifest's floor is the circle's own rule, and a policy engine outside the circle may require more than it and never less. When a circle acts inside an organisation that has its own policy, the two have to agree on which operations each may add requirements to, and on whether the circle can be a tenant of the organisation's decision service at all. That is a design of its own and not started.
20. **New, 2026-10-28.** V1's case. Decided: the panel is taped to the board, not glued into the lid, so the board leaves the case as one unit with its screen; the lid shows the panel through a window with a lip and a frame that stops it lifting, the glass about 3 mm below the top. The expansion port is a 10-pin JST-SH socket on the back edge rather than a pin header, to keep the badge low. Open: whether the flush-glass look is worth a second lid design once the first five are in hand.
21. **New, 2026-10-28.** M4f is split in two. "Chip apps" (M4f) is what the chip does for a seat: it holds the seat key, attests it, and signs SSH logins, git commits, contact cards and grants. It is built and tested against a software chip. "Pad in the chip" (M4j) is the pad key, the ledger counter, encrypted spends and the SCP03 bus encryption. It goes second, because the seat key is the smaller change and the bench teaches what the pad needs. Decided along with it: the circle root is made from the members' reveal content keys, because the pairwise X-Wing secrets differ for each pair of members; git signing needs the commit text and the badge refuses without it; a badge keeps many circles that nothing links; cards travel as files until the station can carry them. Open: whether the manifest or the check words should bind the circle root, since a member who sends different content keys to different members could split it; and where NXP's attestation root and the real attested payload come from. They are read from a real chip on the bench, and until then attestation verifies only the software chip's test CA.
