# Channels Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A circle in the browser app starts a channel, shares a link, and anyone who opens the link reads it and, when the policy allows, posts to it, through a relay rebuilt on SQLite with compile-time features that never put a key on the server.

**Architecture:** A new `no_std` crate, `cahoots-channel`, holds the channel objects (channel, policy, deposit), the link derivation, the per-member key schedule, the version 3 message, the channel grant and its evaluator, and a member session. `cahoots-objects` learns the `cahoots:channel` grant detail and `cahoots-hpke` gains base-mode sealing. The station replaces its JSONL log with SQLite and adds `objects`, `channels` and `gate` Cargo features for storage, per-channel streams and enforcement. The browser app gets channel screens through new wasm bindings over the channel crate.

**Tech Stack:** Rust 2021 (workspace MSRV 1.85, toolchain 1.94), minicbor, p256/ECDSA via `cahoots_core::cose`, ChaCha20-Poly1305, HKDF-SHA256, `hpke` 0.14 (X-Wing), axum 0.7, `rusqlite` with the `bundled` feature, wasm-bindgen, vanilla JS in `web/app`, Playwright for the end-to-end check.

**Spec:** `docs/superpowers/specs/2026-10-30-channels-design.md`

## Global Constraints

- Every crate that the browser or a badge consumes stays `#![no_std]` + `alloc` with `#![forbid(unsafe_code)]`: `cahoots-channel` and the changes to `cahoots-objects` and `cahoots-hpke`. CI builds `cahoots-objects` for `thumbv7em-none-eabi` with `--no-default-features`; `cahoots-channel` joins that line.
- CI runs `cargo fmt --all --check`, `cargo clippy --workspace --all-features --all-targets -- -D warnings`, `cargo test --workspace --all-features`, and the wasm build `cargo build -p cahoots-core -p cahoots-wasm --target wasm32-unknown-unknown`. Every task's commit keeps all four green.
- Every signed object is a canonical CBOR map (integer keys ascending, definite lengths, shortest integers) signed as COSE_Sign1 through `cahoots_core::cose::sign1` with the object's domain as external AAD; decoders re-encode and compare, refusing anything non-canonical, exactly as `crates/objects` does.
- Domain strings, verbatim from the spec: `cahoots/channel/v1`, `cahoots/policy/v1`, `cahoots/deposit/v1`, `cahoots/channel-msg/v1`, `cahoots/channel-id/v1`, `cahoots/channel/epoch/v1`, `cahoots/channel/chain/v1`, `cahoots/link/id/v1`, `cahoots/link/seal/v1`, `cahoots/link/gate/v1`, `cahoots/proof/v1`, `cahoots/grant/v1`, `cahoots/approval/v1`.
- The relay has no key path in any feature but `issuer`, which this plan does not build. No table, endpoint or log line holds an epoch key, a link secret or a seal key; gate tokens are stored as their SHA-256.
- Default station features reproduce today's behaviour and API (`feed-page` on, nothing else). `--log` is replaced by `--db`; there is no migration.
- The link is `https://cahoots.network/app/#/ch/<relay host>/<channel_id hex>/<secret base64url>`. The secret never leaves the fragment.
- Copy in the app follows the project's rules (plain words, no coined names, say what the thing does). The channel screen's label is "End-to-end encrypted; the relay keeps ciphertext only" plus the policy's one-line reading of who can read and post. A channel is never labelled pad-hedged.
- Bump `VERSION` in `web/app/sw.js` once, in the last app task.

## Review Focus

1. A reader who opens a link whose channel has been rotated past that link (no deposit for the link's id at the current epoch) must see "this link no longer works" and not a decryption error. Tests in Task 16 (app) and Task 11 (the relay returns an empty deposit list, not 404).
2. A post whose grant has expired by channel log position (`cahoots-log` ≤ the channel head) must be refused by the relay with `403 {"error":"grant","reason":"expired"}` and dropped by readers. Tests in Task 6 (evaluator) and Task 13 (gate).
3. A message whose COSE signature verifies under a key that holds only a `read` grant must be refused by the relay and shown as unverified by readers. Tests in Task 6 and Task 13.
4. A policy whose `govern` rule has quorum 2 must refuse a replacement policy signed by one seat with one approval. Tests in Task 8 (`verify_governed`) and Task 13.
5. Two readers on the same link must decrypt the same message with independent chain state, and a reader that missed a message must still open later ones within `MAX_SKIP`. Tests in Task 7 (session).
